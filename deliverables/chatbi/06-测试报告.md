## 4. 注入攻击样例回归(硬性验收:全部拦截)

安全断言**直喂校验器**,不经过 LLM——LLM 生成不可控,用它做安全断言没有意义。

| 组 | 样例数 | 拦截结果 |
|---|---:|---|
| 写操作 `UPDATE` / `DELETE` / `INSERT` / `DROP` / `TRUNCATE` / `ALTER` / `REPLACE INTO` / `CREATE TABLE` / `GRANT ALL` | 9 | ✅ 9/9 拦截,理由为「含被禁止的关键字」 |
| 多语句 `SELECT 1; DROP TABLE …` / `SELECT 1;UPDATE …` / `SELECT 1 ; SELECT 2` | 3 | ✅ 3/3 拦截,理由为「只允许单条 SQL」 |
| 注释注入 `--` / `#` / `/* */` / `/*! … */` | 4 | ✅ 4/4 拦截,理由为「含有注释标记」 |
| 越权表:白名单外表 / `mysql.` / `information_schema.` / `otherdb.` | 4 | ✅ 4/4 拦截,理由为「不在白名单内」或「不允许跨库访问」 |
| 危险函数与文件 `LOAD_FILE` / `SLEEP` / `BENCHMARK` / `INTO OUTFILE` / `INTO DUMPFILE` / `@@version` / `@secret` / 子查询藏 `SLEEP` | 8 | ✅ 8/8 拦截 |
| 非 SELECT 开头 `SHOW TABLES` / `EXPLAIN` / `DESCRIBE` | 3 | ✅ 3/3 拦截,理由为「只允许 SELECT 或 WITH 开头」 |
| 长度超限(9000 字符) | 1 | ✅ 1/1 拦截,理由为「SQL 长度超过上限」 |
| **合计** | **32**(其中 30 条为注入专项) | ✅ **全部拦截,拦截率 100%** |

补充断言(SG-04):每条被拒 SQL 的 `reason` 均非空、长度 > 8,且**可直接回灌给模型**让它重写——这是「自检重试」能收敛的前提。

另有一层纵深防御:即使校验器被绕过,数据库侧 `chatbi_ro` 账号本身只有 `SELECT` 授权(`test_integration.py::test_in02_readonly_account_cannot_write` 与 `test_in04_grants_are_select_only` 覆盖)。`test_in05_rejected_sql_never_reaches_database` 进一步验证被拒 SQL **根本没发往数据库**。

## 7. 遗留观察项(非阻断)

| 编号 | 现象 | 影响 | 处置建议 |
|---|---|---|---|
| OB-01 | 端到端单问耗时 2–7 分钟,波动大。瓶颈在 LLM 端点(单次调用 20–75s,含扩展思考),自检打回会重跑整条链路 | 演示可用,但不适合做高并发 | 后续把 `fast_max_tokens` 再压一档,或给自检环节设独立超时降级 |
