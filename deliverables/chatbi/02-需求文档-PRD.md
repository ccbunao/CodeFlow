## 1. 用户与场景

| 角色 | 场景 | 现在的痛 | 期望 |
|---|---|---|---|
| **平台运营** | 「最近 7 天每天新增需求多少条」 | 不知道表叫 `wi_ticket`,也不知道需求要过滤 `type='REQ'` | 一句话,拿到逐日趋势图和一句话结论 |
| **交付负责人** | 「哪个数字员工执行任务最多、成功率多少」 | 成功率的分母含不含 `PENDING` 每次都要重新讨论 | 口径固定在系统里(PENDING 不计入分母但显式说明),结论带样本量 |
| **技术负责人** | 「已完成需求的平均交付耗时」 | 「已完成」到底是进了「验证中」还是「已发布」?耗时从创建算还是从派发算? | 口径写死在系统里:完成 = 流转到 `category='DONE'`;耗时 = 创建 → 进入 DONE |
| **安全负责人** | 「这个 AI 会改我的库吗」 | 无从验证 | 两道独立防线,各自有可复现的证据:校验层拦注入、只读账号被 DB 拒写 |

**主用户故事**:

> 作为平台运营,我希望用业务语言直接问平台自己的业务库,拿到图表和一句带口径说明的结论,而不必知道底层表结构;并且我确信这个过程不会改动任何数据。

## 2. 功能需求

### FR-01 自然语言问答主循环

- **描述**:`python3 -m chatbi "<问题>"` 一条命令完成「生成 SQL → 校验 → 执行 → 自检 → 出图 → 结论」全流程,无需人工干预。
- **验收**:命令退出码 0,标准输出含 SQL、行数、图表文件路径、结论四段。

### FR-02 表选择与 schema 上下文

- **描述**:生成 SQL 前先做一次表选择,只把选中表的字段结构送进生成阶段;表清单与字段结构实时读自 `information_schema`,不写死。
- **理由**:全量 schema(106 表 / 22KB)会让模型把推理预算耗光(实测思考 >16K tokens 仍不产出正文),收敛后同一问题 9.1s 完成。
- **验收**:选表失败时退回核心表并继续;生成提示词只含选中表的字段。

### FR-03 SQL 校验器(防线 A)

- **描述**:SQL 在**发往数据库之前**必须过校验器。仅允许单条 `SELECT`(可带只含 `SELECT` 的 CTE);禁止注释;禁止多语句;禁止 DML/DDL/授权类关键字;禁止危险函数与文件写入;表名必须命中实时白名单。
- **验收**:注入样例集全部被拦;被拦的 SQL **不产生任何数据库侧请求**。

### FR-04 只读执行(防线 B)

- **描述**:以 `chatbi_ro` 账号连接,数据库层只授 `GRANT SELECT ON ainative_v2.*`。
- **验收**:该账号直连执行 `UPDATE` 被 MySQL 拒绝(`1142 UPDATE command denied`),且数据未变。

### FR-05 自检重试

- **描述**:三类失败各自带**可读的修正线索**回灌模型重写——
  1. SQL 被校验器拒绝 → 回灌中文拒绝原因
  2. SQL 执行报错 → 回灌数据库错误信息
  3. SQL 跑通但**结果不对**(如漏 `GROUP BY` 导致结果被折叠成一行)→ 自检环节发现并回灌问题描述
- **上限**:3 次。超限抛错,并打印最后一次 SQL 与全部失败原因。
- **不重试**:查询成功但 **0 行**——空结果通常意味着口径写对了而数据没有,重试只会空转。

### FR-06 图表渲染

- **描述**:输出**单文件 HTML**,ECharts **内联**,断网双击可看。
- **选型**:含日期/时间列且有数值列 → 折线图;行数 ≤ 阈值(默认 20)→ 表格;含分类列且有数值列 → 柱状图;其余 → 表格。
- **注**:时序优先于「行数少」——否则「最近 7 天每天…」这种 7 行时序只会出表格,达不到「出图」的验收。
- **验收**:生成文件内无 `<script src=`,断网渲染无任何网络请求、无 JS 报错。

### FR-07 结论生成

- **描述**:基于**实际查询结果**生成 2–4 句中文结论,先给关键数字再给解读,强制点明样本量;样本量 ≤ 3 行时必须声明「样本量过小」。
- **验收**:结论里出现的数字可在结果里对上;不允许臆造。

### FR-08 平台业务口径固化

- **描述**:把下列口径写进系统提示词,不让模型自由发挥:
  | 词 | 口径 |
  |---|---|
  | 需求 | `wi_ticket.type = 'REQ'` |
  | 新增 | `wi_ticket.gmt_create` |
  | 已完成/已交付 | 工单流转到 `wi_flow_state.category='DONE'` 的节点;完成时刻取 `wi_journal` 中 `event_type='STATUS_CHANGE'` 且 `to_val` 为该状态名的最后一条 `gmt_create` |
  | 交付耗时 | 创建 → 进入 DONE 的小时数 |
  | 数字员工 | `ag_agent`;执行一次任务 = `rt_run` 一行 |
  | 成功率 | `SUCCEEDED / (SUCCEEDED + FAILED)`;**PENDING 不计入分母**,但须在结论中说明排除了多少条 |
  | 空间隔离 | 所有查询限定 `workspace_id`(默认 2) |

### FR-09 配置与密钥

- **描述**:端点读取顺序 `CHATBI_*` → `ANTHROPIC_*` → `chatbi/.env` → 执行器 `runtime.env`(兜底);只读取白名单键;口令与令牌在日志中脱敏;`.env` 不入库。
- **验收**:`chatbi/.env` 被 `.gitignore` 拦截;日志中搜不到口令明文。

### FR-10 演示记录

- **描述**:`demo-session.md` 记录 3 个真实业务问题的 问题 → 生成的 SQL → 行数 → 图表路径 → 结论,命令可在 README 复现。

## 3. 非功能需求(可量化)

| 编号 | 需求 | 指标 |
|---|---|---|
| NFR-01 | 运行时零第三方依赖 | `chatbi/` 的 import 全部落在标准库;不引入任何 site-packages 包 |
| NFR-02 | 图表离线可看 | 生成的 HTML 无外链资源;断网加载时网络请求数 = 0 |
| NFR-03 | SQL 安全 | 注入样例拦截率 100%;被拒 SQL 数据库侧请求数 = 0 |
| NFR-04 | 只读 | `chatbi_ro` 只能 `SELECT`;`UPDATE`/`DELETE`/`DROP` 均被 DB 拒 |
| NFR-05 | 单测 | ≥5 个用例全绿;其中注入攻击样例 ≥20 条 |
| NFR-06 | 密钥卫生 | 代码中零硬编码密钥;日志零明文口令 |
| NFR-07 | 端口与数据源 | 默认 `127.0.0.1:33060` / 库 `ainative_v2`;全部可配置 |
| NFR-08 | 兼容性 | Python 3.11+;宿主实测 3.14.0 |
| NFR-09 | 响应时间 | 简单问题端到端 ≤ 60s(3 次 LLM 调用:选表 / 生成 / 自检) |

## 4. 验收标准(可执行)

| 编号 | 验收项 | 判据 |
|---|---|---|
| AC-1 | 端到端出图出数 | `python3 -m chatbi "最近 7 天每天新增需求多少条"` 退出码 0,产出折线图 HTML + 结论 |
| AC-2 | 单测全绿 | `python3 -m pytest chatbi/tests/ -q` 全绿,用例数 ≥5 |
| AC-3a | 校验层拦注入 | 注入样例全部被拦;被拦 SQL 不触达 DB |
| AC-3b | 数据库层拒写 | `chatbi_ro` 直连 `UPDATE` → MySQL `1142`;数据未变 |
| AC-4 | 演示可复现 | `demo-session.md` 三条命令原样可跑,README 已写明 |
| AC-5 | 图表离线 | 生成的 HTML 断网渲染无网络请求、无 JS 报错 |
| AC-6 | 零依赖 | 全流程仅用标准库;`vendor/echarts.min.js` 本地内联 |

## 5. 明确不做

- 不做写操作(包括建临时表、`INTO OUTFILE`)
- 不做多轮对话记忆、不做会话持久化
- 不做鉴权、多用户、并发隔离
- 不做 BI 语义层、不做指标预计算、不建视图
- 不做非 MySQL 协议的数据源
- 不改平台前后端代码
- 不同步进对外基线仓 `CodeFlow`

## 6. 已知数据约束(影响结论表述,非缺陷)

| 事实 | 影响 |
|---|---|
| `wi_ticket` 全库 11 条,`rt_run` 6 条,`wi_journal` 38 条 | 统计量极小,结论必须带样本量 |
| 全库仅 **1** 个需求到过「已发布」 | 「平均交付耗时」样本 n=1,不能表述为统计结论 |
| `rt_run` 中 2 条为 `PENDING` | 成功率分母排除它们,且必须在结论中说明排除数 |
| 工单跨 5 个 `workspace_id` | 默认只查 `workspace_id=2`,否则数字无法解释 |
