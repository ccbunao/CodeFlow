## 2. 模块职责

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `chatbi/__main__.py` | CLI 入口与参数 | 退出码:0 成功 / 2 配置错 / 3 连不上库 / 4 查询失败 |
| `chatbi/agent.py` | 主循环、提示词、选表、自检、结论、图表调度 | 重试上限 3;0 行不重试 |
| `chatbi/sql_guard.py` | 防线 A:SQL 校验 | 白名单实时读;拒绝原因必须是人话(要回灌给模型) |
| `chatbi/mysql_client.py` | 自研 MySQL wire protocol 客户端 | 纯标准库;只读路径;不支持 TLS/预处理语句 |
| `chatbi/llm.py` | Anthropic 兼容端点客户端 | `urllib.request`;密钥不入日志 |
| `chatbi/chart.py` | 单文件 HTML 渲染 | 内联 ECharts;单元格与标题转义 |
| `chatbi/config.py` | 配置读取顺序、日志脱敏 | 只读白名单键;登记的机密一律 `***` |
| `chatbi/errors.py` | 异常类型 | `SQLRejected` 带 `reason`(回灌用);`MySQLError` 带 `code` 与 `is_permission_denied` |

## 3. 关键决策(含备选与理由)

### D-01 MySQL 连接方式

| 备选 | 优点 | 否决理由 |
|---|---|---|
| **A 自研 wire protocol 客户端**(采纳) | 零第三方依赖;完全掌控协议;可断言「零依赖」这条硬约束 | 工作量最大,是本项目最大不确定性 → 用「与 `mysql` CLI 同 SQL 结果一致」交叉验证兜底 |
| B PyMySQL | 现成、健壮 | **违反仓库规范**(`docs/00` §4 零第三方运行时依赖);需求方明确「不许豁免」 |
| C subprocess 调 `mysql` CLI | 零协议实现 | 依赖外部二进制;转义与输出解析脆弱;无法拿到列类型(图表选型要用) |

**事实前提**:`default_authentication_plugin=mysql_native_password`,实测 `root@%` 的插件是 OceanBase 同算法别名 `ob_native_password`——两者算法一致,客户端一并支持。

### D-02 ECharts 进单文件的方式

| 备选 | 优点 | 否决理由 |
|---|---|---|
| **A 内联 vendor**(采纳) | 真单文件;离线可看;演示环境不会白屏 | 每个文件约 1MB——可接受 |
| B CDN 引用 | 文件小 | 离网即废;与「离线可看」冲突 |

实测 `cdn.jsdelivr.net` 可达,但演示环境不保证有外网。

### D-03 图表选型:时序优先于「行数少」

需求原文「数据行数少出表格、时序出折线、分类出柱状」三条有重叠。**若「行数少」优先**,「最近 7 天每天新增需求」只有 7 行 → 出表格 → **达不到「出图出数」的验收**。故定为:

1. 含日期/时间列且有数值列 → 折线图
2. 行数 ≤ 阈值 → 表格
3. 含分类列且有数值列 → 柱状图
4. 其余 → 表格

时序列的判定:列类型属 `DATE/DATETIME/TIMESTAMP`,或列名含 `date/day/time/dt/month/week/日期/时间/月份/天`。

### D-04 两阶段选表(性能关键)

**问题**:全量 schema(106 表 / 1013 字段 / 22KB)直接进生成提示词,模型会把推理预算耗光——实测 `max_tokens` 提到 16384 仍只输出 thinking、无正文;而只给 5 张相关表时,同一问题 **9.1s / 1224 tokens** 就完成。

**方案**:加一个**选表阶段**——先把紧凑表名清单 + 前缀语义送给模型,让它挑 ≤6 张表;再只把这些表的字段送进生成阶段。

**兜底**:
- 选表调用失败 → 退回核心表(`wi_ticket` / `wi_journal` / `wi_flow_state` / `ag_agent` / `rt_run`)
- 核心表恒定并入(口径规则引用到它们)
- 生成后数据库报「表/列不存在」→ 自动切全量 schema 再试一次

**代价**:多一次 LLM 调用(约 5–10s),换来生成阶段提示词从 22KB 降到 2–4KB。

### D-05 自检放在执行之后

需求原文的顺序是「执行 → **自检重试** → 图表+结论」,所以自检是**执行之后**的复核,不是执行前的校验。它拦的是「SQL 跑通但答案不对」——实测最典型的是**用了聚合却漏 `GROUP BY`**,结果被折叠成一行,数据看着「正常」实则答非所问。

自检由 LLM 复核,输出 JSON `{ok, problem, conclusion}`:`ok=false` 则把 `problem` 回灌重写。

**确定性辅助信号**:若 SQL 含聚合函数却无 `GROUP BY`,或结果只有 1 行,自检提示词里会显式提示「可能漏了分组维度」——把确定性信号喂给模型判断,而不是自己写死规则。

### D-06 两层只读防线

| 层 | 手段 | 能拦什么 | 拦不住什么 |
|---|---|---|---|
| A 应用层 | SQL 校验器 | 注入形态、多语句、DML、越权表 | 若校验器自身有洞 |
| B 数据库层 | `chatbi_ro` 只授 `GRANT SELECT` | 任何写操作,**无论 SQL 怎么来** | 读到的敏感数据(靠 A 层的表白名单收敛) |

两层互补且**各自独立可验**。验收文字按 B 层落(需求原文「错误账号连库执行 UPDATE 必须被拒」),但 A 层才是产品自身的防线,两条都要测。

### D-07 拒绝原因必须是人话

校验器的拒绝信息会**回灌给模型**让它重写,因此必须是「中文 + 可执行线索」,而不是「syntax error」。例如:

- ✅「SQL 含有注释标记 '--',只允许无注释的单条查询」
- ✅「表 'foo' 不在白名单内;可用表: ag_agent, ag_ai_message, …」
- ❌「invalid sql」

### D-08 结论由第二次 LLM 调用生成

不靠模型在生成 SQL 时「顺便」下结论——那时它还没看到数据。改为执行后把**问题 + SQL + 结果摘要(含前 20 行)**再送给模型,要求它只依据给定数据作答、必须点明样本量。

**降级**:自检输出解析失败或调用失败时,退到一次独立的结论生成;再失败则输出确定性的兜底文本。**任何一环失败都不能让整轮查询崩掉**。

## 4. 故障处理矩阵

| 故障 | 检测点 | 处理 | 用户可见 |
|---|---|---|---|
| 端点不可达 / 超时 | `llm.complete` 抛 `LLMError` | 立即失败,不静默降级 | 「无法连接 LLM 端点 …」 |
| 响应被 `max_tokens` 截断 | `stop_reason == "max_tokens"` 且无正文 | 报错并提示调大 `CHATBI_ANTHROPIC_MAX_TOKENS` | 明确的调参指引 |
| 数据库连不上 | `MySQLClient.connect` | 退出码 3 | 「无法连接数据库 …」 |
| 账号权限不足 | `MySQLError.code in (1044,1142,1143)` | 透传错误 | 「UPDATE command denied to user 'chatbi_ro'@'%'」 |
| SQL 被校验器拒绝 | `SqlGuard.check` 抛 `SQLRejected` | 带原因回灌重写,上限 3 次 | 自检/拒绝记录 |
| SQL 执行报错 | `MySQLError` | 带错误回灌重写 | 重试记录 |
| 表/列不存在 | 错误信息匹配 `_UNKNOWN_OBJECT_RE` | 切全量 schema 再试 | 「已切换到全量表结构…」 |
| 结果被折叠(漏 GROUP BY) | 自检返回 `ok=false` | 带问题描述回灌重写 | 自检拦截记录 |
| 查询 0 行 | `row_count == 0` | **不重试**,出「无数据」结论 | 结论 + SQL + 可能的口径偏差提示 |
| 自检输出不是合法 JSON | `_parse_verdict` 返回 `None` | 降级到独立结论生成 | 正常出结论 |
| 重试耗尽 | 循环结束仍无结果 | 抛错,打印最后一次 SQL 与全部失败原因 | 完整失败链 |

## 5. 数据流与状态

```
状态机(单次问答):
  SELECT_TABLES ─→ GENERATE ─→ VALIDATE ─→ EXECUTE ─→ SELF_CHECK ─→ CHART
                      ▲            │           │            │
                      └────────────┴───────────┴────────────┘
                            (拒绝/报错/自检不通过,带线索回灌,≤3 次)

  EXECUTE ─(0 行)─→ 结论(无数据),不再自检
```

## 6. 安全设计要点

- 校验器在**发往 DB 之前**判定,被拒 SQL 不产生任何数据库侧请求(单测断言)
- 表名白名单**每次会话实时读** `information_schema`,不写死
- 跨库访问直接拒绝(schema 前缀只允许 `ainative_v2`)
- 注释一律禁止(`--` `#` `/* */`)——注释是注释注入的主要载体
- 危险函数与文件写入(`LOAD_FILE` / `SLEEP` / `INTO OUTFILE` / `@@` / `@`)一律禁止
- 生成的 HTML 对标题、列名、单元格全部转义,防 `<script>` 注入
- 口令与令牌经 `config.redact()` 脱敏,`.env` 被 `.gitignore` 拦截
