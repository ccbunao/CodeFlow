## D-01 · 2026-11-20 · P0 · 列定义包解析越界崩溃

- **现象**:自研 MySQL 客户端握手成功,但执行任何查询时在 `_parse_column_def` 抛 `IndexError: index out of range`,取不到任何数据。
- **根因**:MySQL 列定义包(Protocol::ColumnDefinition41)的第 7 个字段是 **length-encoded integer**(固定字段长度,典型值 `0x0c`),不是 length-encoded string。我按「前 6 个都是字符串」的惯性把它当成长度编码字符串读,于是额外吃掉了 12 个字节,后面读列类型时越界。协议里 string 与 int 两种长度编码前缀相同(首字节 <0xFB),光看字节分不出来——必须按**字段语义**区分,读文档时把两者混为一谈了。
- **修复**:`_parse_column_def` 中该字段改用 `read_lenenc_int`。
- **回归验证**:`MC-07` 握手解析 + L2 `IN-01` 真实查询返回正确列名与类型码。
- **状态**:`已修复(已回归)`

## D-02 · 2026-11-20 · P2 · 测试夹具 scramble 字节数写错

- **现象**:`MC-07` 断言 `auth_plugin == "mysql_native_password"` 实际得到空串。
- **根因**:真实握手的 `auth_plugin_data_part_2` 是 **12 字节数据 + 1 字节 NUL 终止符**(共 13),我的夹具用 `bytes(range(8,21))` 造了 13 字节数据再拼 NUL,变成 14 字节;解析器按 `auth_plugin_data_len` 消费 13 字节后,插件名起始位置偏移 1 字节,读到的第一个字节正好是 NUL → 空串。**是夹具写错,不是解析器错**——但这类「协议字节数差一」的错最容易让人误判成实现有 bug,所以记下来。
- **修复**:夹具改为 `bytes(range(8, 20)) + b"\x00"`。
- **回归验证**:`MC-07` / `MC-08` 通过;并用真实 seekdb 握手交叉验证(`server_version` 读出 `5.7.25-OceanBase`)。
- **状态**:`已修复(已回归)`

## D-03 · 2026-11-20 · P0 · 全量 schema 撑爆模型推理预算,查询无法完成

- **现象**:「哪个数字员工执行任务最多」这条问题**永远出不来结果**。`max_tokens` 从 2048 提到 8192、16384 均失败,响应里 `output_tokens_details.thinking_tokens` 占满预算,`stop_reason=max_tokens`,只有 thinking 块没有正文。同一问题改成只喂 5 张相关表的字段结构后,9.1 秒、1224 tokens 就完成。
- **根因**:把「把库结构告诉模型」当成了不需要论证的既定条件。平台库有 106 张表、1013 个字段,压成一行一张表仍有 22KB。模型要先在 106 张表里定位目标,推理链被拉长到远超输出预算。**提示词体积直接挤占推理预算**——这是把「上下文更全」误当成「更好」,没算这笔账。
- **修复**:引入**两阶段选表**。先用一个紧凑提示词(表名清单 + 前缀语义)让模型挑 ≤6 张表,生成阶段只带这些表的字段;核心表恒定并入。生成后若数据库报「表/列不存在」,自动切全量 schema 再试一次。
- **回归验证**:`AG-02`(生成提示词不含全量 schema)、`AG-03`(未知表自动切全量)、L3 三个演示问题全部在预算内完成。
- **状态**:`已修复(已回归)`

## D-04 · 2026-11-20 · P0 · 响应被 max_tokens 截断时,正文为空且提示不准

- **现象**:报错「LLM 返回了空内容」,但实际根因是 `stop_reason=max_tokens`——模型把预算全花在扩展思考上,正文根本没开始写。
- **根因**:默认 `max_tokens=2048` 是按「普通对话」的直觉定的,没考虑该端点的模型会先输出一大段 thinking;而 thinking token **同样计入** `max_tokens`。另外响应解析只按 `type=="text"` 取块,thinking 块被丢弃后与「真的没内容」混为一谈。
- **修复**:默认 `max_tokens` 提到 32768;解析时区分「有 thinking 无正文且 `stop_reason=max_tokens`」与「真空内容」,前者给出「请调大 `CHATBI_ANTHROPIC_MAX_TOKENS`」的明确指引,不再笼统报错。
- **回归验证**:L3 三个演示问题在 32768 下全部产出正文;L0 `LLMClient._extract_text` 覆盖 thinking + text 混合响应。
- **状态**:`已修复(已回归)`

## D-05 · 2026-11-20 · P1 · 时序数据出表格,达不到「出图」验收

- **现象**：「最近 7 天每天新增需求」返回 7 行,图表形态是 **table** 而不是折线图。
- **根因**:需求原文「数据行数少出表格、时序出折线、分类出柱状」三条规则**互相重叠**,我按字面顺序把「行数少」放在最前,7 < 20 于是先命中表格。时序规则根本没机会生效。而验收要求是「能直接**出图**出数」——出表格不算出图。
- **修复**:选型改为「时序优先」:有日期/时间列且有数值列 → 折线图,先于行数阈值判定;分类且有数值列且行数 ≥2 → 柱状图;行数 ≤ 阈值 → 表格;单行汇总仍出表格(平均耗时做成一根柱子没有意义)。
- **回归验证**:`CH-01`、`CH-05`、`CH-06`;L3 三个演示问题分别产出折线图、柱状图、表格。
- **状态**:`已修复(已回归)`

## D-06 · 2026-11-20 · P1 · 排名类问题把结果折叠成一行

- **现象**：「哪个数字员工执行任务最多」生成的 SQL 用 `RANK() OVER (...) = 1` 只取第一名,返回 1 行,画不出图,结论也无法展示其他候选。
- **根因**:提示词的口径规则只规定了「怎么算」,没规定「**返回多少**」。模型按字面理解「哪个最多」= 只给答案,没意识到 BI 场景需要可对比的候选集。**口径要管到结果的形状,不只是算法**。
- **修复**:口径规则增加第 10 条——排名类问题必须返回全部候选并按指标排序,第一名由结论指出;配合 D-05 的选型调整(分类且 ≥2 行 → 柱状图)。
- **回归验证**:L3 E2E-02 产出全部候选的柱状图;`CH-05` 锁定「少量多行分类 → 柱状图」。
- **状态**:`已修复(已回归)`

## D-07 · 2026-11-20 · P1 · 重试历史只保留最后一条,错误原因被挤掉

- **现象**:数据库报「表不存在」后切全量 schema 重试,但回灌给模型的线索里**只剩**「已切换到全量表结构」,原始的数据库错误信息不见了。
- **根因**:写 `history[-1:]` 是为了控制提示词长度,但「切全量 schema」这条追加在错误信息**之后**,于是把刚要说的错误原因挤了出去——省提示词省掉了最关键的信息。
- **修复**:改为 `history[-2:]`,同时保留错误原因与切换说明。
- **回归验证**:`AG-03` 断言回灌内容里同时含「执行失败」与「全量表结构」。
- **状态**:`已修复(已回归)`

## D-08 · 2026-11-20 · P1 · SQL 被拒时的原因不可用于修正

- **现象**:校验器拒绝 SQL 时只给出笼统信息,模型拿到后无法针对性改写,白白耗掉重试次数。
- **根因**:把校验器当成「布尔闸门」,没意识到它的**拒绝信息本身是回灌给模型的输入**——它是纠错链路的一环,不是给人看的日志。
- **修复**:拒绝原因统一改为「中文 + 可执行线索」,例如「表 'foo' 不在白名单内;可用表: ag_agent, ag_ai_message, …」「SQL 含有注释标记 '--',只允许无注释的单条查询」;并加 `AG-05` 断言回灌内容含具体线索。
- **回归验证**:`SG-04`(每条被拒 SQL 的 reason 非空且长度 > 8)、`AG-05`。
- **状态**:`已修复(已回归)`

## D-10 · 2026-11-20 · P1 · 时间列被当成 UTC,整体平移 8 小时

- **现象**:「最近 7 天每天新增需求」生成的 SQL 里出现 `DATE(CONVERT_TZ(w.gmt_create, '+00:00', '+08:00'))`——把库里存的时间当成了 UTC 再转成东八区。本批数据恰好没有 16:00 之后创建的工单,所以**数字看起来完全正确**,掩盖了问题。
- **根因**:没弄清平台时间列的存储语义就写口径。平台用 `serverTimezone=Asia/Shanghai` 连库,`DATETIME` 列里存的是 **Asia/Shanghai 本地墙钟时间**;模型默认「库里存的都是 UTC」,于是加了一层 `CONVERT_TZ` 平移。**这是一个错误被正确数字掩盖的缺陷**——最危险的一类。
- **判定依据(实证,非推断)**:数据库 `id_user.username` 里带有脚本写入的 epoch 后缀 `persona_e2e_1795128081`,该 epoch 的 UTC 时刻是 `2026-11-19 22:41:21`,渲染成 +08:00 是 `2026-11-20 06:41:21`,与库里该行的 `gmt_create = 2026-11-20 06:41:21` **逐字吻合** → 库里存的是 +08:00 本地墙钟时间。
- **修复**:① 口径规则明确写死「时间列存的就是本地墙钟时间,直接 `DATE(gmt_create)`,**禁止 `CONVERT_TZ` 平移**」;② 自检复核要点增加「时间口径有没有搞错」,显式点名 `CONVERT_TZ` 平移是错的。
- **回归验证**:重新生成的 Q1 SQL 不含 `CONVERT_TZ`,直接用 `DATE(gmt_create)`;`CURDATE()` 取今天(服务器时区 +08:00)。
- **状态**:`已修复(已回归)`
