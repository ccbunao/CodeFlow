# usage-guide.md · 在 CodeFlow 平台创建并使用「公众号标题优化师」数字员工

- 目标读者:第一次在本平台创建数字员工的业务同事
- 平台地址:`http://localhost:7001`(容器 `platform-app-1`)
- 配套文件:`agent-prompt.md`(人设全文与设计说明)、`agent-config.json`(可直投 API 的配置)、`test-cases.md`(验收用例)
- 说明:本指南与 `agent-prompt.md` 第 1/2 节、`agent-config.json` 的 `soulMd` / `agentMd` **逐字一致**。三处内容必须同步,改一处要改三处(本指南 §2 给了核对命令)

---

## 0. 前置条件

| 项 | 要求 |
|---|---|
| 平台可访问 | 浏览器打开 `http://localhost:7001`,已登录 |
| 运行器在线 | 左侧「执行与自动化 → 运行节点」里,至少一个执行节点状态为在线;否则派发会排队等待 |
| 数字员工可创建 | 左侧「执行与自动化 → AI 数字员工」能打开列表页 |

## 1. 创建数字员工

左侧「执行与自动化 → AI 数字员工」→ 右上角「创建数字员工」(或直接访问 `http://localhost:7001/agents/new`)。

表单从上到下共 6 项,按下面的表逐项填:

| # | 表单项 | 填什么 | 必填 |
|---|---|---|---|
| 1 | 名称 | `公众号标题优化师` | 是 |
| 2 | 头像 | 留空即可(见 §6 已知限制) | 否 |
| 3 | 角色名称 | `公众号标题优化师` | 是 |
| 4 | 角色编码 | `TITLE_COACH` | 是 |
| 5 | SOUL.md | 下面 §1.1 的全文 | 否,但本员工必填 |
| 6 | AGENT.md | 下面 §1.2 的全文 | 否,但本员工必填 |

> 角色编码是自由输入的,平台预置项里没有 `TITLE_COACH`,直接手输即可(大写下划线风格,和现有 `FS_DEV` / `CR` 一致)。

### 1.1 SOUL.md 粘贴以下全文

```text
你是 CodeFlow 平台的「公众号标题优化师」数字员工。

你服务于中文微信公众号的内容编辑场景:编辑给你一篇正文,你产出可以直接拿去排版的候选标题,让读者在信息流里一眼想点开。

你的判断只依据正文本身。正文里没有的数字、时间、机构名、收益承诺,标题里一律不出现;正文没说清楚的事情,你不会替它编。你不确定正文到底想说什么时,先反问编辑一句,不要硬猜着往下写。

你熟悉中文标题的常见套路(痛点式、反常识式、具体收益式、对比式、疑问式),但不会为了凑套路牺牲准确 —— 一个准确的平铺直叙,好过五个似是而非的爆款。
```

### 1.2 AGENT.md 粘贴以下全文

```text
## 工作方法

1. 通读正文,先确定三件事:写给谁、解决什么问题、读者读完能带走什么。
2. 找出正文里信息量最大的那一点(通常是具体收益、踩过的坑、或者与常识相悖的结论),标题围绕它发力。
3. 五个候选要覆盖不同角度,建议在直给结论、痛点共鸣、反常识悬念、具体收益、身份代入里各取其一。彼此之间要有区分度,不是同一句话的换词改写。
4. 标题只使用正文里出现过的信息,正文没写的不要替它写。

## 输出格式

每次回复固定输出五个候选,顺序即推荐度从高到低,格式如下:

1. 标题:<不超过 20 字的标题>
   理由:<一句话,不超过 40 字,说明这个标题抓的是正文里的哪一点>
2. 标题:<标题>
   理由:<理由>
3. 标题:<标题>
   理由:<理由>
4. 标题:<标题>
   理由:<理由>
5. 标题:<标题>
   理由:<理由>

## 硬约束

- 恰好 5 个候选,一个不多一个不少。
- 每个标题不超过 20 字(标点计入),超了必须改写后再输出。
- 每条理由一句话,不超过 40 字。
- 不写开场白、不写「以下是」、不用 markdown 表格、不解释你的思考过程。
- 正文信息不足以支撑 5 个有区分度的标题时,先反问编辑要关键信息,不要凑数。
```

填完点「创建」,页面跳转到该数字员工的详情页。

## 2. 验证人设真的存住了

在详情页确认两处正文与 §1.1 / §1.2 一致:

- 「配置」区域的 `SOUL.md` 一栏显示 §1.1 的内容;
- `AGENT.md` 一栏显示 §1.2 的内容。

如果这两栏是空的,说明人设没有落库 —— 重新创建一次,并把 `test-cases.md` A1 的结果反馈给平台维护者。

也可以直查数据库确认:

```bash
docker exec platform-seekdb-1 mysql -h127.0.0.1 -P2881 -uroot ainative_v2 \
  --default-character-set=utf8mb4 \
  -e "SELECT id,name,role_code,LENGTH(soul_md) soul_len,LENGTH(agent_md) agent_len
      FROM ag_agent WHERE name='公众号标题优化师'"
```

`soul_len` 与 `agent_len` 都应大于 0(本员工预期分别约 720 / 1314 字节)。

## 3. 让它干活

### 3.1 派发一个需求(走完整交付流程)

1. 「需求录入」→ 新建需求,标题写例如「给本周技术周报出一组候选标题」,描述里粘上正文。
2. 需求详情 →「启动交付」→ 选编队、选成员(选「公众号标题优化师」)→ 确认。
3. 平台把任务包下发给运行器,任务包里的 `identity.json` 带着这个员工的 SOUL.md / AGENT.md;
   运行器据此组装系统提示词,产出按 `deliverables/` 目录约定回传,在需求的「产物区」可见可下载。

### 3.2 直接对话(快速取标题)

「AI 数字员工」→ 点进「公众号标题优化师」→ 在输入框粘正文 → 发送。
回复应当是 5 个候选标题,每个不超过 20 字,每个后面跟一句理由。

## 4. 澄清与产物归档

在需求详情发起澄清时,数字员工的每一轮澄清结论会被归档成该需求的产物:

- 产物落在需求详情页的产物区,文件名形如 `clarification-turn-2.md`;
- 它属于「未关联执行」分组(澄清不是一次派发执行);
- 可以被后续澄清作为附件引用:`附件` 区选该产物,下一轮澄清的正文会自动带上 `[附件] clarification-turn-2.md`。

要看澄清结论不用再翻聊天记录:直接下载产物文件即可。

## 5. 后续维护

| 动作 | 入口 | 注意 |
|---|---|---|
| 改人设 | 数字员工详情 → 编辑 | 编辑页的 SOUL.md / AGENT.md 两栏直接显示当前人设;只改「角色名称」而不管人设两栏时,人设**保持原值不会被清空**;要清空就把该栏显式删空再保存 |
| 看历史版本 | 数字员工详情 → 版本 | 每次「提交」会存一份配置快照(含 SOUL.md / AGENT.md);回滚会把两份正文一起恢复 |
| 备份导出 | 平台「配置备份」 | 导出内容已包含 SOUL.md / AGENT.md 两列 |

## 6. 已知限制

| 限制 | 影响 | 说明 |
|---|---|---|
| 头像不落库 | 表单第 2 项填了也保存不下来 | 平台当前没有存放头像的字段(`ag_agent` 表无该列),与本员工交付无关,留空即可 |
| 数字员工没有「描述 / 标签 / 参数」字段 | 配置只能落在这 6 项里 | 需要额外信息时写进 SOUL.md / AGENT.md 正文 |
| 会话内没有 `mcp__ainative__*` 工具 | 数字员工在会话里查不到平台数据 | 平台下发会话帧时不带 MCP 令牌,已登记缺陷;需要平台数据时在澄清附件里提供 |
| 版本详情接口不返回人设正文 | 详情页版本对比里「草稿」一侧的 SOUL.md / AGENT.md 显示 `-` | 该接口只回配置快照 JSON,没拆出 soulMd / agentMd 两列,已登记缺陷(不在本次范围);当前人设本身在详情页与编辑页都正常显示,不影响使用 |
| 派发后改人设不影响已发出的任务包 | 改完立刻重跑同一个需求,结果仍是旧人设 | 这是有意设计:任务包按派发时快照执行,保证包体可复现。要用新人设就发起一次新的派发 |

## 7. (可选)用 API 一次创建

`agent-config.json` 的字段与创建表单一一对应,可直接投递:

```bash
curl -X POST http://localhost:7001/api/agents \
  -H "Authorization: Bearer <你的 accessToken>" \
  -H "Content-Type: application/json" \
  --data-binary @deliverables/agent-config.json
```

| config 字段 | 对应表单项 | 平台字段(`ag_agent` 列) |
|---|---|---|
| `name` | 名称 | `name` |
| `avatarUrl` | 头像 | 无(平台不落库) |
| `roleName` | 角色名称 | `role_name` |
| `roleCode` | 角色编码 | `role_code` |
| `soulMd` | SOUL.md | `soul_md` |
| `agentMd` | AGENT.md | `agent_md` |

返回体里 `soulMd` / `agentMd` 为空即说明没存上,参考 §2 排查。
